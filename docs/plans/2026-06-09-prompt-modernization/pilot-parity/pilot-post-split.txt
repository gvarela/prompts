## (3) Verification gate sequence per worker, including retry policy

For each worker, after it returns:

1. **Gate 0 — completion check**: `bd show ${taskId}` must show `status: closed`. If `in_progress` → worker crash path: do **NOT** run verification; follow the Worker Failure Playbook and present the user 4 options (retry same context / retry with additional context / mark blocked and investigate / manual intervention).
2. **Gate 1 — verification agent**: spawn `wb:task-verifier` with the "Verification Agent Prompt" inputs: Task ID, Task Description, Test Command, Files Changed, Tests Modified, Worker Summary. It runs tests, checks scope adherence, returns markdown containing `### Status: PASS` or `### Status: FAIL`.
3. **Parse autonomously**: `passed = report.includes("### Status: PASS")`; `failed = report.includes("### Status: FAIL")`.
4. **On PASS**: add to success log, aggregate modified files/test commands/notes, run `bd ready`, proceed to next task.
5. **On FAIL — retry policy (max 2 automatic fix retries)**:
   - **Retry 1**: spawn fix worker (general-purpose agent, **opus** model) with Task ID, original task description, verification report, and instruction to fix the specific issues and close the beads issue. Then **re-verify** with the task-verifier using the same context.
   - **Retry 2** (if still FAIL): repeat the fix-worker spawn with additional context from the second verification report. Then re-verify.
   - **After 2 failed retries**: add the task to the blocking-issues list for phase checkpoint review and **continue to the next task** (failures surface at the phase boundary; individual task failures don't block autonomous flow).
